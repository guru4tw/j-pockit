1. 一張圖看懂

分工原則一句話:想清楚、寫下來、切成票交給 mattpocock-skills(Pocock);動手、驗證、審查、出 PR交給 pstack。pstack 自己的說明就寫明它沒有 planning skill[1],所以規劃段只能用 Pocock[2]。

2. 設定(一次性)

指令頻率做什麼
/setup-pstack每台機器一次依可用模型選每個角色用哪個模型、多少 reasoning budget,寫成 ~/.claude/rules/pstack-models.md。非 Claude 的模型名在 Claude Code 下由 adapter 退回 session 模型。
/setup-matt-pocock-skills每個 repo 一次設定該 repo 的 issue tracker、triage label、domain 文件放哪。

兩者沒有先後,也不互斥。

3. 規劃 / 規格 / 票:Pocock

步驟指令產出
1/grill-with-docs一題一題逼問到計畫沒有模糊處,邊問邊寫 ADR 與 GLOSSARY.md。
2/to-spec把剛才討論整理成一份 spec,發到 issue tracker。不再問問題。
3/to-tickets把 spec 切成一組 tracer-bullet 票,每張標明被哪張擋住。

4. 執行 / 驗證 / 審查 / PR:pstack 為主

開工前先開 /poteto-mode,整段都在這個工作風格下做:回覆精簡、刻意分派 subagent、文字去 AI 腔、程式碼保持簡單、做完要驗證。

要做什麼指令哪套
改之前先看懂既有程式怎麼跑、東西該放哪層/howpstack
工作量大、可拆:開 N 個平行 worker,收成一份報告/swarmpstack
逐票實作/implement(內部叫 /tdd、/code-review)Pocock
多個 reviewer 從不同角度挑戰設計或改動/interrogatepstack
依 repo 規範與原始 spec 兩條軸審 diff/code-reviewPocock
寫 PR 說明prPocock
刪掉文字裡的 AI 腔/unsloppstack
為什麼 tdd 裝 Pocock 版:Pocock 的 /implement 是使用者叫的 orchestrator,它會自動叫 model-invoked 的 /tdd。換成 pstack 版,這條鏈就斷了。

5. 回顧

  • /retro(Pocock):對一段開發 session 做回顧。
  • /reflect(pstack):開三個 review subagent 掃本次對話,把學到的東西落成某個既有 skill 的具體修改。想直接改 skill 時用它。

6. 單 session 捷徑

小改動不必走完整條。Pocock 自己建議的短路線是 /grill-with-docs → /implement[2]:問清楚就直接做,跳過 spec 與票。執行時照樣可以開 /poteto-mode。

附錄 B. 技術關鍵字術語表(口語化說明)

關鍵字類別口語化說明 / 來源#
pstackskill setLauren Tan 的 56 個 skill,偏執行、驗證、審查。j-pockit 裝其中 55 個(不裝 tdd)。 [1]
mattpocock-skillsskill setMatt Pocock 的 skill 集,偏規劃、寫 spec、切票。j-pockit 裝 engineering + productivity 共 25 個。 [2]
/setup-pstackpstack skill一台機器跑一次,決定 pstack 各角色用哪個模型、給多少推理預算。 [1]
reasoning budget設定值模型每次可以花多少推理量。pstack 分 unlimited / large / medium / small 四檔。 [1]
~/.claude/rules/pstack-models.md檔案/setup-pstack 寫出的 rule 檔,每個專案都會套用,蓋過 skill 內建的模型預設。 [1]
adapterpstack 文件~/.claude/docs/harness/claude-code.md,把 pstack 原本給 Cursor 的寫法對應到 Claude Code(工具名、模型名、檔案路徑)。每個 pstack skill 開頭都會叫你先讀它。 [1]
/setup-matt-pocock-skillsPocock skill每個 repo 跑一次,告訴 Pocock 的 skill 這個 repo 的票開在哪、label 怎麼叫、文件放哪。 [2]
issue tracker概念放 spec 與票的地方,可以是 GitHub Issues,也可以是 repo 裡一張票一個檔。 [2]
/grill-with-docsPocock skill對計畫連續追問,問到沒有模糊處,同時把決定寫成 ADR 與術語表。 [2]
ADR文件類型Architecture Decision Record,一個重要決定一份短文件:當時的情況、選了什麼、為什麼。 [2]
GLOSSARY.md文件專案術語表。Pocock v1.3 起由 CONTEXT.md 改名而來,舊專案要自己改名。 [2]
/to-specPocock skill把目前對話整理成 spec 發到 issue tracker,只做彙整不再訪談。 [2]
/to-ticketsPocock skill把計畫或 spec 切成一組票,每張寫明被哪幾張擋住。 [2]
tracer-bullet切票方法每張票都是從頭到尾打通的一條細路徑(UI 到資料都碰一點),做完就能跑、能驗,而不是按層切。 [2]
/poteto-modepstack skillpstack 的常駐工作風格:回覆精簡、刻意用 subagent、文字去 AI 腔、程式簡單、做完要驗證。 [1]
subagentClaude Code 機制主對話派出去做一件事的子代理,有自己的 context,只把結論帶回來。 [3]
/howpstack skill解釋某個子系統怎麼運作、資料怎麼流、東西該放哪個 package / 哪一層。改程式前先跑。 [1]
/swarmpstack skill同時開 N 個平行 worker 做同一類工作,全部收回後合成一份報告。 [1]
/implementPocock skill照 spec 或票實作一件工作;使用者手動叫,內部會叫 /tdd、/code-review。 [2]
/tddPocock skill測試先行:先寫會失敗的測試,再寫剛好讓它過的程式,再整理。 [2]
/code-reviewPocock skill從某個基準點起的改動,分「是否符合 repo 規範」與「是否符合原始 spec」兩條軸審,兩個 subagent 平行跑。 [2]
/interrogatepstack skill找多個 reviewer 各從一個角度挑戰改動,專找盲點。 [1]
prPocock skill寫 PR 說明。取材自 Dex Horthy(HumanLayer)的 show-me。 [2]
/unsloppstack skill把文字裡一看就是 AI 寫的痕跡刪掉。 [1]
model-invokedskill 類型模型可以自己判斷要叫的 skill。反過來,frontmatter 寫 disable-model-invocation: true 的只能由使用者打 /名字 叫。Pocock 規定使用者叫的可以叫模型叫的,反向不行。 [2] [3]
/retroPocock skill對一段開發 session 做回顧。 [2]
/reflectpstack skill開三個 review subagent 掃本次對話,把心得落成既有 skill 的具體修改。 [1]
