1. 一張圖看懂

分工原則一句話:想清楚、寫下來、切成票交給 mattpocock-skills(下稱 Pocock);動手、驗證、審查、出 PR交給 pstack。pstack 自己的說明就寫明它沒有 planning skill[5],所以規劃段用 Pocock[2]。

2. j-pockit 要解決什麼:兩套各補哪個缺口

兩套 skill 各自完整,但重心不同。Pocock 強在人和 AI 先對齊:把模糊的想法逼問清楚、用同一套名詞、寫成 spec、切成每張都能單獨驗的票。pstack 強在AI 動手時的紀律:改之前先看懂、設計多做幾個比較、讓不同模型互相挑錯、做完拿證據、長時間跑留決策紀錄。

面向Pocockpstack
核心信念先對齊理解;好的回饋迴圈就是 skill 本身做完要能證明;第一個設計通常不是最好的
叫法使用者叫的 orchestrator,內部再叫模型自己叫的 discipline幾乎全部設了 disable-model-invocation,只能由你打指令,再由 /poteto-mode 統一調度
入口/ask-matt:只告訴你該叫哪個,不會替你執行/poteto-mode:挑一套 playbook 照步驟做;/poteto-help:只回答該用哪個
規劃逼問 → spec → 票刻意沒有;用 prototype 回答問題,設計定了才寫 plan
驗證測試先行 + 兩軸 code review看真東西、專案自己的驗證 skill、效能數字七問、影響範圍檢查
回顧改善 agent 的工作環境把心得改進 skill;讓同一個錯在結構上不可能再犯

簡單說:Pocock 回答「要做什麼、做到哪算完」,pstack 回答「怎麼做才不出包、怎麼證明做對了」。

j-pockit 做的事很少:把兩套扁平裝進 ~/.claude/skills/,用短名直接叫(/how,不是 /pstack:how),版本釘死,並處理三個同名衝突[4]:

名稱裝哪版理由
/tddPocockPocock 的 /implement 會自動叫 /tdd;換成 pstack 版這條鏈會斷
/teachpstackpstack 版會串 /how、/why
/handoff都不裝 Pocock 版同名時 skill 會蓋掉本機的 /handoff 指令

為什麼不用官方 plugin 方式安裝,見 ADR 0001[9]。

3. 設定(一次性)

指令頻率做什麼
/setup-pstack每台機器一次依可用模型決定每個角色用哪個模型、多少 reasoning budget,寫成 ~/.claude/rules/pstack-models.md。最後會問要不要建專案的驗證 skill,建議答應(見 5.6)。
/setup-matt-pocock-skills每個 repo 一次一次問一題、每題附建議答案:(A) issue tracker 用 GitHub、GitLab 還是 repo 內的 markdown;(B) triage label 怎麼叫;(C) domain 文件放哪。結果寫進 docs/agents/,並在既有的 CLAUDE.md 加一段 ## Agent skills。

兩者沒有先後,也不互斥。補充三點:

  • /setup-pstack 是 pstack 裡唯一模型可以自己叫的 skill。沒跑過也能用,各角色會用 skill 內建的預設模型。
  • 選 local markdown 當 issue tracker 時,spec 和票放在 .scratch/<feature>/,一張票一個檔,檔內有 Status:、Blocked by: 兩行。
  • Pocock v1.3 起 CONTEXT.md 改名 GLOSSARY.md,沒有向下相容,舊專案要自己 git mv。

4. 規劃 / 規格 / 票:Pocock

Pocock 的 skill 分兩種[7]:你打名字才會跑的 orchestrator,和模型判斷需要時自己叫的 discipline。規則是 orchestrator 可以叫 discipline,反過來不行。所以 /grill-with-docs 本身很薄,真正做事的是它叫的 grilling 和 domain-modeling。

4.1 主流程

步驟指令什麼時候產出
1/grill-with-docs(不在 repo 裡就用 /grill-me)有新想法、計畫還模糊共同理解、ADR、GLOSSARY.md
2(選用)/prototype有問題要跑一下才知道答案丟棄式程式 + 結論
3/to-spec要跨多個 session 才做得完一份 spec
4/to-ticketsspec 定了一組 tracer-bullet 票
5/implement(逐票)或 /implement-spec(整份平行)開工commit
6/retro做完,尤其做得不順時環境改善建議

context 的規矩:步驟 1、3、4 留在同一段不中斷的 context 裡;prototype 另開 session 做,做完把結論帶回來;每個 /implement 開新的 context。

4.2 /grill-with-docs:逼問加留紙本

這是整套最重要的一步。它的做法:

  • 把計畫看成一棵決策樹。每一輪把前置條件都已決定的那一層問題(frontier)一次列出來,每題附它建議的答案,你只要逐題回「同意」或改。
  • 查事實是 AI 的事,做決定是你的事。能從程式碼查到的,它派 subagent 去查,不會拿來問你。
  • 邊問邊由 domain-modeling 更新 GLOSSARY.md:挑戰跟術語表衝突的用詞、把含糊的詞說死(「account」到底是 Customer 還是 User)、編邊界情境來測、拿你說的去對程式碼。難回頭又有真實取捨的決定才寫 ADR。
  • 問到沒有待決問題才停,而且你確認理解一致之前不會動手。

用法提示:用 /grill-with-docs 不要用 /grill-me,前者多留了紙本,下一個 session 讀得到。

4.3 /to-spec 與 /to-tickets

/to-spec 只做彙整,不再問問題。它先用術語表的名詞讀 repo、遵守既有 ADR,再跟你確認測試要放在哪幾個 seam(「越高越少越好,理想是一個」),然後寫出:問題、解法、一長串 user story、實作決定、測試決定、不做什麼。spec 裡不寫檔案路徑和程式碼,因為那些很快就過時。

/to-tickets 把 spec 切成票。每張票是一條從頭打通到尾的細路徑(每一層都碰一點),做完就能展示、能驗,而且一個新 context 裝得下。需要先整理的「prefactoring」排最前面。大範圍重構例外,改用 expand-contract 排序。它會跟你來回確認切法和誰擋誰,你點頭才發票,每張標 ready-for-agent。

注意:/to-spec 和 /to-tickets 會直接發到 issue tracker,選 GitHub 就會開出真的 issue。沒跑過 /setup-matt-pocock-skills 時,多數 Pocock skill 會先停下來叫你去跑。

4.4 /implement 與 /implement-spec

/implement/implement-spec
範圍一張票(或單 session 的整件事)整份 spec 的所有票
誰開車你逐張叫,每張之間 /clearAI 當調度者,把票當成任務圖
做法在事先講好的 seam 用 /tdd;常跑 typecheck 和單一測試檔,最後跑全套;跑 /code-review;commit 到目前 branch開一條 integration branch;能做的票各派一個背景 subagent、各用一個 worktree;另有一個 merger 收合;全部做完跑 /code-review 再修
適合想自己盯每一步票多、彼此相依清楚,想讓 AI 平行做

4.5 模型自己叫的三個:/tdd、/code-review、pr

  • /tdd:先寫一個會失敗的測試,再寫剛好讓它過的程式,一個一個來,不先把測試全寫完。測試只放在事先講好的 seam,只在系統邊界(外部 API、時間、亂數)mock,不 mock 自己的 module。重構不在這個迴圈裡,交給 code review。介面形狀本身有疑問時會叫 codebase-design。
  • /code-review:對某個基準點以來的 diff,分兩條軸各派一個 subagent 平行審。Standards 軸看 repo 規範(加 12 個 Fowler code smell 當底線),Spec 軸看有沒有照原始 spec 做。兩軸結果分開列,不合併排序。基準點(main 或某個 SHA)沒給會問你;找不到 spec 就略過 Spec 軸。
  • pr:寫 PR 說明時自動套用。三段:最小的一張圖說重點、改前改後的證據(截圖最好,測試輸出次之)、合併風險(能不能回頭、影響多大)。

4.6 支線入口:修 bug、整理 issue、超大工作

情況指令重點
東西壞了、很慢、測試失敗/diagnosing-bugs第一步一定是建一個能穩定重現失敗、跑得快、AI 自己能跑的回饋迴圈。沒有能變紅的指令,就不准開始猜原因。再來是縮小重現、列 3 到 5 個可推翻的假設(測之前先給你看排序,你可以改;你不在就照它的排序)、一次只改一個變數加 log、有合適的 seam 就先寫回歸測試(沒有的話這本身就是發現,要記下來)、清掉 debug log。
issue 堆積/triage每個 issue 一個類別(bug / enhancement)、一個狀態(五個標準 label)。先查是否重複、是否已被拒絕過,再重現。AI 發的留言一律加免責聲明。/to-tickets 產的票不要再 triage。
超大、霧很濃、一個 session 裝不下/wayfinder畫一張由決策票組成的地圖,一個 session 只解一張票(研究票除外)。它只做規劃不做實作,最後回到主流程的 /to-spec。範圍清楚的功能不要用它。

4.7 其他 Pocock skill 速查

指令叫法什麼時候用
/improve-codebase-architecture你叫有空檔時做架構健檢。產出一份 HTML 報告列出可「加深」的模組,你選一個再進逼問;結果回流 /grill-with-docs。
/prototype模型叫要驗證狀態邏輯(單一 HTML 檔 + 可點的按鈕)或 UI 長相(同一頁 3 到 5 個結構不同的變體,用 ?variant= 切)。答案寫進正式程式碼並從 issue 指過去;原型程式碼本身留在 prototype/<name> branch 當一手資料。
/research模型叫派背景 agent 只查一手來源,寫成一份附引用的 markdown。
codebase-design模型叫deep module 的詞彙與原則:小介面藏大量行為、介面就是測試面。「Design it twice」會派 3 個以上 subagent 各用不同限制設計介面再比較。
/to-questionnaire你叫答案在別人腦袋裡時,產一份問卷給對方填。
/wait-what你叫AI 上一則沒講懂,要它用簡化英文加術語表的詞重講。
wizard模型叫設 CI secret、第三方後台這類 AI 做不了的手動步驟,產一支一步一步帶你做的 bash 腳本。
writing-for-agents模型叫寫給 agent 讀的文件(skill、CLAUDE.md)的寫法參考;/retro 會用到。

4.8 context 什麼時候清:階段邊界五選一

Pocock 把 context 管理當成流程的一部分。只在階段邊界做決定,照順序問,第一個「是」就照做:

  1. 繼續:下一階段需要這段對話當一手資料,或 smart zone(約 150k token)還夠。
  2. /clear:目前的 context 跟下一步無關。
  3. /handoff:換工具、換目錄、交給同事,或中途分出一條支線。
  4. subagent:那件事 AI 自己做得完。
  5. /compact:預設選項,但不是第一個想到的。

理由:除了「繼續」,其他做法都會把一手資料變成有損的摘要。階段中途 compact 最傷,新 session 會很有自信地照著被壓扁的摘要做錯。

5. 執行 / 驗證 / 審查:pstack

pstack 是 Lauren Tan(poteto)的工作方式[1][5]。幾乎每個 skill 都要你親手打指令;實務上你只要記住一個入口 /poteto-mode,其他 skill 由它在需要時拉進來。

5.1 /poteto-mode 怎麼運作

  1. 讀 Claude Code 的 adapter,把 Cursor 的工具名、模型名換成這裡的。
  2. 把你的任務對到 23 套 playbook 之一,把那套的步驟原樣抄成待辦清單。跳過的步驟要寫 skip: <理由>,所以你看得到它省略了什麼。都對不上或範圍很大時,改走 /figure-it-out 現場設計一套。
  3. 依觸發表自動拉其他 skill:非小改動先 /how;程式碼跨函式邊界就 /architect;設計有爭議就 /interrogate;寫文字套 /unslop;review 前跑 /no-comments;有效能數字就 /benchmark-checklist;長時間或無人看管就 /show-me-your-work。
  4. 套用到的每條 principle,回覆裡要點名,並說它改變了哪個決定。
  5. 可回頭的工作直接做不問你;只在 force-push 共用 branch、部署、刪資料、對客戶發訊息前停下來。要問你「選哪個做法」之前,跑一下就知道答案的先用 prototype 回答。它也被要求該反對時就反對。
  6. 分派 subagent 用 poteto-agent,每件事開新的,主 agent 要親自看過每個 diff。
  7. 回覆風格:短句、不用破折號、每個說法標明是量到的、推論的還是猜的。

5.2 23 個 playbook 速查

你不必背 playbook 名字,用平常的話描述任務,/poteto-mode 會自己對。下表方便你知道有哪些路可走,以及用什麼說法會被導到那裡。

類別playbook做什麼 / 觸發說法
弄清楚Investigation唯讀調查,附引用的答案。說「don't change any code yet」。
Runtime forensics對活著的程式加量測,不靠讀原始碼猜。
Trace forensics從已抓到的 profile、trace、heap snapshot 診斷。
Session pickup接手別人(或上週的你)做到一半的 branch,讀決策紀錄,不重做已完成的。
改程式Bug fix先在真實介面重現,用執行期證據找根因,再修。說「repro first」。
Feature從具名的資料形狀開始做新功能。
Refactoring結構變、行為不變。說「zero behavior change」。
Perf issue每個修正都要對到 baseline 量測。
Hillclimb對一個指標持續改進:假設、改、量、記錄,每個進步一個 commit。
Visual parity新舊畫面要一模一樣,用影像比對判定。
設計與規劃Prototype丟棄式草稿回答設計問題,附截圖或時間給你比。
Multi-phase plan設計定了之後寫 plan:一個 PR 一節,每節結尾是證明它有效的方法。只寫不做。
出貨Opening a PR每套 playbook 結尾都跑,開 PR。
Babysit把 PR 顧到可合併(review thread、CI)。遇到衝突只回報哪條 branch 要 rebase,不自己解。
Shipping每個 PR 單獨驗,只合從根算起連續驗過的那段。
Autopilot-full一串互不相依的 PR,各有負責的 subagent 從建到合。
Autopilot-stack一條線性堆疊的 PR,交給你審和合。
長跑Autonomous run給一個可檢查的完成條件,一路做到條件成立。
Orchestrate跨好幾天、很多 PR 的大計畫,一個調度者管一群 subagent。
Pause safely你說要暫停時,收尾或退回目前這步、存檔、寫接手說明。
維護Authoring a skill寫新 skill。「拿不準就刪」。
Eval改 skill 或 prompt 前先做盲測實驗,避免「知道在被測」影響結果。
Worktree cleanup清掉已合併或放棄的 worktree。

23 套都對不上時,/poteto-mode 改叫 /figure-it-out 現場設計一套。

5.3 先看懂:/how、/why、/teach、/recall

AI 出錯通常是兩種:誤會你要什麼,或缺 context 就動手。這四個解第二種,而且都逼 AI 用你能檢查的話解釋自己[5]。

指令回答什麼做法prompt 範例
/how程式現在怎麼跑、新東西該放哪小問題直接讀;大子系統先派 2 到 4 個唯讀 explorer 分頭看,再由一個 explainer 整合。輸出:概觀、關鍵概念、流程、東西在哪、陷阱。/how do we dedupe notifications?
/why為什麼長這樣、這個數字哪來的從 git blame / log 起頭,再依你接了哪些 MCP 平行查 issue、文件、聊天、監控等 7 類證據。分開「直接證據」和「推論」,查無結果也照實報。/why was the retry limit set to five?
/teach讓你真的懂跑 /how 和 /why,用白話加逐步長大的圖解釋。加一句「convince me」,解釋就變成你能檢驗的論證。/teach me how this PR changes retries. convince me it fixes the cause.
/recall你自己最近做到哪翻你最近的對話紀錄、PR、branch,整理成現況、各線狀態、問題、下一步。/recall catch me up on the export work from last week

坑:別因為「AI 反正會讀程式」就跳過這步。沒先建好心智模型就動手,常會在第一個看起來合理的地方修症狀。

5.4 設計:/architect、/arena、/swarm、/interrogate

  • /architect:先跑 /how(搬動擁有權時加 /why)打底,再用 /arena 產出至少兩個結構不同的設計草稿,每個都先寫「呼叫端怎麼用」,再寫型別與簽名。預設設計完直接實作;要先看設計就說「with checkpoint」。實作中如果到處出現同樣的繞路、只能靠 any 或強制轉型才編得過,它會當成設計錯了,砍掉重來。
  • /arena:N 個 subagent 做同一份題目,各寫在自己的目錄或 worktree;一個唯讀評審(盡量用不同模型家族)照評分表打分;主 agent 選一個當底,再從每個落選者嫁接一兩個好點子(候選收斂時就不用嫁接),最後驗證。決定很貴時就要求更多候選。
  • /swarm:把工作切成互不相干的片,一片一個 worker,各回 PASS / ISSUES / BLOCKED,最後一份報告。缺結果算缺口,不算通過。要覆蓋面用 swarm,要比設計用 arena。
  • /interrogate:把同一個 diff 交給不同模型家族的 reviewer。重點是模型差異,不是角色扮演;兩個模型各自都抓到的問題最可信。主 agent 把結果分成 Act on / Consider / Noted / Dismissed,每個駁回都附理由,不會自動套用。駁回的也要看,你可以推翻。

多少設計工作才夠?pstack 給的設計階梯[5]:

情況用
小改動、做完了但不放心只跑 /interrogate
跨函式邊界或搬擁有權/architect(會帶上 /arena)
單一決定:命名、格式、演算法直接 /arena
覆蓋矩陣、平行檢查、競速/swarm
跑一下就知道答案的問題(版面、時間、做法)prototype,不要辯論
有爭議、事後很難改的設計/architect,出貨前再 /interrogate
跨好幾個 PR設計定了之後寫 plan

/poteto-mode 已經會照這個階梯自動做。你直接叫它們,通常是想要比預設更多或更少的檢查。

5.5 寫與清:/unslop、/no-comments、/technical-writing

  • /tdd:j-pockit 裝的是 Pocock 版(見 4.5)。pstack 的 Bug fix playbook 說「用 tdd skill」時,拿到的就是這一版。
  • /unslop:依一份編號清單刪掉 AI 腔,例如誇張詞彙、破折號、句中冒號、粗體開頭的條列、聊天機器人用語、抽象比喻名詞。/poteto-mode 每則回覆都會套。
  • /no-comments:review 前派 comment-sicko(一個痛恨註解的 subagent)掃 diff。主 agent 會審它的判斷;描述限制的註解,會提議改成型別、執行期檢查、測試或 lint;你同意就改完再刪註解,不同意也照刪,並回報這個限制還沒有被保護。
  • /technical-writing:文件、RFC、README、PR 說明、commit message。一份文件只選一種模式(教學、操作、參考、解說),目標是「累了的工程師第一遍就看懂」。

5.6 驗證:證明做對了

pstack 最核心的一條原則是 prove-it-works:看真正的東西,不看替代指標;「編得過」「測試綠了」都不算證明。驗證失敗時,先懷疑是觀察方法錯了。

指令做什麼結果
/create-verification-skill為專案產生 verify-<app> skill:怎麼啟動、怎麼自檢、怎麼操作、怎麼留證據、怎麼收拾,外加一份功能地圖。它會實際跑一遍確認證據留得下來。/setup-pstack 跑完會主動提議做這一步。專案內的 skill 目錄
/maintain-verification-skillApp 改了,功能地圖就會過時。逐項重驗、補漏clean / changed / blocked 三選一
/create-formal-verification-skill併發、重試、狀態機、parser 這類測試很難碰到的性質,用 TLA+ 之類做形式驗證形式模型 + 檢查腳本
/benchmark-checklist回報或依效能數字行動前問 7 題:為什麼不是兩倍?有調過嗎?有超限嗎?有出錯嗎?能重現嗎(交替跑 5 次以上)?端到端有差嗎?工作真的有做嗎?變快 / 變慢 / 沒有可量測差異 / 無法判定,附數字、單位、次數、範圍、瓶頸
/blast-radius小 diff 不放心時,找它會在別處弄壞什麼。重點不是列呼叫者,而是 grep 找不到的那種(版本、時序、wire format、DB 欄位、feature flag),並找出「它安全是因為哪一個事實」,寫腳本跑真程式證明風險清單(含 file:line)、已排除項、合併前要做的事

5.7 長跑與夜跑

能自己驗證的 agent,才能放著讓它跑。放手前先確認四件事都成立[5]:

  1. 你自己做過一次,或看 agent 做過一次,知道「好」長什麼樣。
  2. agent 有你會用的工具和訊號:驗證 skill、profiler、log。
  3. 每個階段都會證明自己的成果,不達標能讓整條線停下。
  4. 你讀過幾份紀錄,並把重複出現的失敗做成工具、skill 或檢查。

還沒全成立就在旁邊看著跑。夜跑的交代要有:目標、可判定的完成條件(「done means ...」)、獨立的 worktree、事先給的權限(「don't ask me before committing」)、卡住時的出口(「truly stuck 就停下寫原因」),最後用 /loop 跑到條件成立。

  • /figure-it-out:先寫出可推翻的完成條件,把工作切成最小單位、風險最高的先做,驗證工具和 baseline 先建。每圈:假設、最小改動、量、留或退。
  • /show-me-your-work:每個決定記一列到 decisions.tsv(時間、階段、決定、理由、證據、結果),只追加不改,預設只留在本機不 commit。結束時先對照紀錄自我稽核,再請不同模型的 reviewer 看。早上用 /show-me-your-work catch me up on what you did last night 驗收。
  • 迴圈的節奏:一次改一個東西、驗一次、記一列。沒幫助的改動丟掉。完成條件不准偷偷放寬。

指令用途

7. pstack 怎麼解 AI 使用者的痛點

pstack 的做法是把「人得一直盯著的事」寫成 skill 裡固定會跑的步驟。下表左欄是用 AI 寫程式常見的痛,右兩欄是 pstack 的對應。

痛點pstack 的解法機制
AI 誤會你要什麼prompt 五要素(9.1)、/in-your-own-words、/sharpen開工前把目標和完成條件說死,再讓 AI 複述
不懂既有程式就動手,修到症狀/how、/why;Investigation playbook非小改動一律先建心智模型;說「don't change any code yet」只出調查結果
第一個設計就定案/architect、/arena、prototype多個候選、交叉評審、選底再嫁接;能跑的問題用跑的回答
同一個模型自己審自己,盲點一樣/interrogate不同模型家族各審一次,兩邊都抓到才是強訊號;駁回要附理由
「build 綠了」就說完成prove-it-works、verify-<app>對真正的產物驗證,檢查寫成可重跑的腳本
效能數字不可信/benchmark-checklist七問找瓶頸、排除量錯東西
小改動在別處炸開/blast-radius找出「安全靠的那一個事實」並跑程式證明
文字一股 AI 腔、註解氾濫/unslop、/no-comments編號規則逐條掃;另派 subagent 專挑註解
長跑回來不知道 AI 做了什麼決定/show-me-your-work每個決定一列紀錄 + 異模型 review
離開一下就跟不上/ketchup、/recall、Session pickup只整理你沒看到的部分,並列出等你決定的事
同一個錯一直手動糾正/correct、encode-lessons-in-structure 原則重複的提醒改成 lint、型別、測試,而不是多寫一段說明
主對話被大量輸出塞爆guard-the-context-window 原則大量讀檔交給 subagent,主對話只留結論
AI 一直問「要繼續嗎?」never-block-on-the-human 原則可回頭的事直接做完再給你看;只在不可逆的事前停
不知道該叫哪個 skill/poteto-mode、/poteto-help由 playbook 決定步驟,你只描述任務

8. 別重踩作者的坑

8.1 pstack 作者列的 14 個坑

這些是 pstack 指南最後一頁整理的常見錯誤[5],右欄是改法。

#坑為什麼會出事改成這樣

8.2 Pocock 列的坑

  • 階段中途 /compact,新 session 會照被壓扁的摘要做錯。只在階段邊界決定(4.8)。
  • 對 /to-tickets 產的票再跑 /triage。
  • 範圍清楚的功能用 /wayfinder;或把地圖直接丟給 /implement,跳過 /to-spec。
  • 沒有能變紅的回饋迴圈就開始猜 bug 原因。回歸測試放在太淺的 seam,只換來假的安心。
  • mock 自己的 module、測實作細節、先把測試全寫完再寫程式。
  • spec、票裡寫檔案路徑和程式碼;GLOSSARY.md 寫實作細節。
  • 寫給 agent 的文件用否定句(「不要想大象」反而會想);用正面描述目標。

9. 善用技巧

9.1 prompt 五要素

要素說明例
目標要達成什麼背景工作每幾小時就 timeout,要找出原因
完成條件能判 pass / faildone means 連跑 24 小時零 timeout
要看到的證明你要什麼證據才信給我用了哪些資料、各假設的證據
已知的事你手上有的事實,不是猜測上週升級 DB driver 後開始

不要寫「怎麼做」和「你猜的原因」。換任務時說「new task」讓它重挑 playbook。後續追問用短句就好,例如「do it」「continue」。

9.2 用原則名當方向盤

pstack 的 24 條原則各是一個 skill,/poteto-mode 每次會讀索引、套用、在回覆點名。你覺得它方向偏了,直接在 prompt 裡點原則名就能修正,比長篇解釋有效。

9.3 兩套怎麼接,不打架

  • 逼問和 prototype 分工:Pocock 的逼問處理只有人能回答的問題(意圖、名詞、取捨);pstack 的 prototype 處理跑一下就知道的問題。兩個都用,不要拿 prototype 問意圖,也不要逼問一個跑一下就知道的問題。
  • spec 不要 /interrogate:pstack 作者明講抽象的 plan 不值得花 reviewer;它該用在 diff 上。spec 的品質靠逼問和 /to-tickets 的確認環節。
  • pstack 沒有 planning,Pocock 補上:多 PR 的工作,先 Pocock 逼問 + spec + 票;每張票開工時打 /poteto-mode 做票 #N,讓 pstack 的 playbook 接手執行與驗證。
  • 兩種 review 可以都跑:Pocock /code-review 看「合不合規範、合不合 spec」;pstack /interrogate 看「不同模型能不能把它弄壞」。前者對齊意圖,後者找 bug。
  • 修 bug 選一條:/diagnosing-bugs 強在先建回饋迴圈、假設清單;/poteto-mode 的 Bug fix playbook 強在執行期證據和分派。推測:單機能重現的用前者,要在真實環境量測的用後者。
  • 回顧兩個都有用:/retro 改環境,/reflect 改 skill,/correct 改 repo。

9.4 控制成本

  • /setup-pstack 選小一點的 budget。
  • 不重要的角色用 auto 或 inherit-parent,也就是跟著 session 的模型。
  • /arena、/interrogate 少開幾個候選或 reviewer。
  • /poteto-mode 留給真的需要嚴謹的工作,小事直接講。

11. 情境速查與單 session 捷徑

情境建議路線
新功能,要好幾個 session/grill-with-docs → /to-spec → /to-tickets → 每張票 /poteto-mode(或 /implement)→ /interrogate → PR → /retro
小改動/grill-with-docs → /implement(Pocock 自己建議的短路線[2]),執行時照樣可以開 /poteto-mode
修 bug/poteto-mode + 「repro first」,或 /diagnosing-bugs(見 9.3)
看不懂舊程式/how;想知道歷史加 /why;要真的懂用 /teach
架構健檢/improve-codebase-architecture → 選一個候選 → /grill-with-docs
效能問題/poteto-mode(Perf issue)+ /benchmark-checklist
超大、還很模糊/wayfinder → 一個 session 解一張決策票 → /to-spec
要睡了讓它跑四條件成立後:/poteto-mode + 完成條件 + worktree + /loop;早上 /show-me-your-work
離開一下回來同一個對話用 /ketchup;跨對話用 /recall
不知道用哪個規劃類問 /ask-matt;執行類問 /poteto-help
